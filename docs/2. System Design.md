## 3. Software Architecture

요구사항을 바탕으로, 시스템의 기능들을 동시에 처리해야 하는 역할 단위로 나눈다. 아래 그림은 각 RTOS가 어떤 역할을 하며, 서로 어떤 데이터를 주고받아 전체 시스템에 동작하는지 보여준다. 

<img width="1089" height="842" alt="image" src="https://github.com/user-attachments/assets/3b06ba26-6d30-48f4-90cb-88883e2b1723" />

### **3.1.1. 이벤트 발생 및 데이터 생성 (파란색)**

- `ButtonInputTask` :
    - 버튼이 눌리면 외부 인터럽트가 발생하여 깨어남
    - 어떤 버튼인지 판별 후 `g_command_queue`에 명령(`command_msg_t`)을 전송
- **`SecurityEventTask`**:
    - 200ms마다 초음파 측정을 수행
    - Echo 핀 인터럽트가 발생하면 거리를 계산하고, 침입 조건이 충족되면 `g_security_event_group`에 이벤트 비트를 세트
- **`CANCommTask`**:
    - CAN 수신 인터럽트 발생 시 콜백을 통해 깨어남
    - 수신된 데이터를 파싱 후 `g_command_queue`에 명령 메시지를 전송
    - 2000ms 주기로 현재 시스템 상태(`g_system_status`)와 센서 데이터(`g_latest_sensor_data`)를 CAN으로 송신
- **`SensorTask`**:
    - 1000ms 주기로 센서(온습도/조도/VR)를 읽어옴
    - 수집된 데이터(`sensor_data_t`)를 `g_sensor_data_queue`에 전송

### **3.1.2. 데이터 교환 허브 (노란색)**

- **RTOS Message Queues**
    - `g_command_queue` : 버튼 입력, CAN 수신 명령이 모이는 곳
    - `g_sensor_data_queue` : 주기 센서 데이터가 모이는 곳
        
        → 각 태스크는 직접 통신하지 않고 **큐를 매개**로 비동기적으로 동작 → 모듈 독립성과 안정성 확보.
        
- **전역 데이터 (Mutex 보호)**
    - `g_system_status` : 시스템 모드, 알람 여부 저장 (`g_system_status_mutex` 보호)
    - `g_display_data` : FND와 OLED 표시할 최신 데이터 저장 (`g_display_data_mutex` 보호)
- **EventGroup**
    - `g_security_event_group` : 보안 이벤트 발생 비트를 세트 → `MainControlTask`가 주기적으로 확인

### **3.1.3. 중앙 처리 및 의사 결정 (초록색)**

- **MainControlTask**
    - `g_command_queue`, `g_sensor_data_queue`에 이벤트가 들어오기 전까지 Blocked 상태
    - 명령을 받으면 현재 모드에 따라 장치 제어 로직 실행
    - **센서 데이터**를 받으면 모니터링 모드/수동 모드 로직 수행 (예: 팬/조명 자동 제어, VR 기반 밝기 조절).
    - **보안 이벤트** 발생 시 알람 상태 전환, 부저와 LED 점멸 시작
    - 모든 처리 결과를 반영하여 `g_display_data` 업데이트

### **3.1.4. 최종 출력 (빨간색)**

- **Actuator 제어**
    - Servo (DoorLock), Step Motor (Blinds), Relay (External Power)
    - Fan, Main Light, RGB LED, Security LED, Piezo Beep, Buzzer
- **Display**
    - **DisplayTask** : 1초마다 `g_display_data`를 읽어 OLED/FND 표시를 갱신
    - **FNDScanTask** : 2ms 주기로 실행, 멀티플렉싱 방식으로 FND를 빠르게 갱신 → 깜빡임 방지
